# Финальный отчет по ДЗ (Practice 05)

## 1. Альтернативный SDD‑фреймворк и сравнение с OpenSpec

- Выбранный альтернативный фреймворк: OpenAPI 3.1 (Design‑First).
- Ключевые свойства OpenAPI 3.1:
  - Машиночитаемый контракт в YAML/JSON, совместимый с JSON Schema 2020‑12.
  - Строгие схемы валидации запросов/ответов, переиспользуемые компоненты (schemas, parameters, responses).
  - Богатая экосистема: генерация типов/клиентов/серверных заглушек, валидация на ранних этапах, интеграции с CI/CD и тестовыми раннерами.

- Сравнение с OpenSpec:
  - OpenSpec: ориентирован на естественный язык в Markdown, встроен в CLI кодинг‑агента; управляет изменениями через контекст (rules/instructions) и артефакты изменения. Подходит для SDD с участием LLM, быстро фиксирует договоренности в «живом» процессе разработки.
  - OpenAPI: жесткий протокольный стандарт, независимый от LLM. Задает строгий формат контрактов и валидируемых схем.

- Плюсы/минусы подходов:
  - OpenAPI — плюсы: стандартность, строгая проверяемость, зрелые инструменты (генерация клиентов/серверов/моделей), повторное использование схем, совместимость с QA/безопасностью. Минусы: многословность, кривая обучения, меньшая гибкость для неструктурированных частей и быстрых итераций «на словах».
  - OpenSpec — плюсы: высокая скорость согласования через естественный язык, тесная интеграция с агентом, управление изменениями через контекст, удобство для SDD. Минусы: риск неоднозначностей, меньше формальных гарантий и внешних инструментов, зависимость от корректной интерпретации LLM и дисциплины ведения контекста.

Вывод: в этой работе OpenAPI 3.1 использовался как «жесткий» каркас для логики и валидации, а OpenSpec — как управляемая артефактами оболочка процесса согласования (UI ↔ Logic) и реализации.

## 2. Процесс согласования двух спецификаций

Расхождения в версиях «ДО»:
- Имена параметров поиска: UI использовал `q`, Logic — `query`.
- Значение статуса «все»: UI — `status=all`, Logic — отсутствие параметра (`status` опускается).
- Пагинация/метаданные: UI — объект `pagination` с `page/perPage`, Logic — объект `meta` с `page/limit`.
- Структура ошибок 400: UI рекомендовала оболочку `error: { code, message, details }` и коды наподобие `invalid_query`; Logic — плоский объект `{ code, message, details }`, детали с полем `path` и код `BAD_REQUEST`.

Как расхождения устранены в согласованном контракте и версиях «ПОСЛЕ»:
- Параметр поиска унифицирован на `query` (см. `contract.md`, п. «Запрос GET /api/items»).
- Статус «Все» трактуется как отсутствие параметра `status` (см. `contract.md`: «Если выбрано "Все", параметр не передается»).
- Метаданные пагинации унифицированы в `meta` с полями `page, limit, total, totalPages` (см. `contract.md` и `spec_logic_after.yaml`). UI‑спецификация «ПОСЛЕ» отражает `meta` вместо `pagination`.
- Ошибка 400 стандартизована как `{ code: "VALIDATION_ERROR", message, details: [{ field, message }] }`. В `spec_logic_after.yaml` и `contract.md` детали указывают `field`, а не `path`; код — `VALIDATION_ERROR`.

- Контракт: `docs/contract.md`.
- После: `docs/spec_ui_after.md`, `docs/spec_logic_after.yaml`.

## 3. Сквозные проверки и реализация

Тест‑кейсы из `practices/practice_05/test.js` покрывают ключевые сценарии по контракту:
- Успешный запрос 200 OK: тело содержит `data` (массив) и `meta.page` (число).
- Фильтрация и поиск: запрос `status=active` возвращает только активные элементы; поиск по `query` регистронезависим, в том числе для не‑ASCII (пример: «Документ»).
- Пустой результат (empty state): при отсутствии совпадений — 200 OK, `data: []`, `meta.total = 0`, `meta.totalPages = 0`.
- Валидация 400: если `query` короче 2 символов — `400 Bad Request`, тело ошибки `{ code: 'VALIDATION_ERROR', details: [{ field: 'query', ... }] }`.

Эти проверки служат «сквозными»: от контракта → реализации сервера → подтверждение соответствия посредством e2e‑теста.

## 4. Рефлексия

- Чему научил подход с согласованием контракта ДО генерации кода: ранняя фиксация терминов и структур (имена параметров, формат метаданных, ошибки) минимизирует переделки и рассинхроны между командами UI/Logic. Контракт становится единственным источником истины для разработки, тестирования и документации.
- Почему ручное решение архитектора важно при стыковке двух независимых агентов: автоматизация/LLM ускоряют работу, но не снимают ответственности за семантические решения и компромиссы. Архитектор обеспечивает непротиворечивость, выбирает «каноническую» форму (например, `query` и `meta`), решает коллизии (например, `all` → опущенный `status`) и закрепляет их в контракте/артефактах, чтобы агенты действовали согласованно.
